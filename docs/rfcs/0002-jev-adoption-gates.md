# [RFC-0002] Jev Cold Path 分阶段接入与接管门禁

- **作者**：Codex
- **状态**：草稿，待评审；不代表已批准生产外发或自动治理
- **创建日期**：2026-09-23
- **关联议题**：[统一分类契约 #60](https://github.com/munger-lab/hippo/issues/60)、[Jev 适配器 #61](https://github.com/munger-lab/hippo/issues/61)、[离线评测 #62](https://github.com/munger-lab/hippo/issues/62)

## 背景与目标

现有 Cold Path 已把关系分类与确定性胜者仲裁分开。Jev 的 Choice API 可对候选事实对返回 `EQUIVALENT`、`CONFLICT`、`DISTINCT` 的概率，但这些概率尚未在 Hippo 的中文、英文和中英混合数据上校准，不能直接作为合并授权。

目标是先用合成记忆对验证协议和故障弃权，再用隔离数据评估质量、时延、token 成本，最后在明确外发边界和独立审核后考虑旁路与限定接管。默认部署必须继续使用既有分类器；任何 Jev 故障不得改变原记忆。

非目标：让 Jev 生成事实文本、决定赢家、替换 Mem0、增加 Agent MCP 参数，或在本 RFC 阶段启用生产数据外发。

## 已落地的安全边界

- #60 的 `RelationshipClassificationBackend` 只接收 ID 与事实文本；协调层在调用前复核身份、活跃状态和精确文本规则。时间、来源与确认数只交给 `WinnerArbiter`。
- #61 提供显式构造的 `JevClient` 与注入式 HTTP 传输；固定模型 `jev-1.13.0`、问题版本 `memory-relation-v1`，验证完整概率、所选类别、模型 ID 和响应大小。服务失败产生可审计弃权代码；不记录密钥或原文。
- 目前 `JevRelationshipClassifier` 无论 Jev 选哪一类，均向治理层返回 `DISTINCT`；三分类和两种不同的置信信息仅存审计证据。默认路径不创建客户端，也不出网。

## 后续阶段与门禁

| 阶段 | 交付 | 晋级条件 |
| --- | --- | --- |
| 离线评测（#62） | 与检索 qrels 分离的成对数据集、录制响应、按关系和语言切片的报告 | 人工语义标签作为真值；校准/测试按事实簇隔离；错误合并、弃权、概率分桶、时延和成本均可复现 |
| 旁路观察（#63） | 现有分类器主判，Jev 仅在调用方显式注入与项目 allowlist 下记录匿名差异 | 明确获准外发的数据范围及调用预算；Jev 故障、超时或响应变化对 plan/apply 零影响；不在默认 CLI 自动启用 |
| 阈值选择（#64） | 版本化、可复现的模型/rubric/数据集校准产物 | 分别评估等价与冲突门槛及覆盖率；中文和混合语言不能被总平均掩盖 |
| 限定接管（#65） | 显式部署开关及回滚说明 | 校准产物与当前模型/rubric 匹配，误治理风险和数据条款经人工认可，保持既有身份、版本、幂等 apply 围栏 |

## 备选方案与风险

维持现有 LLM 是零新增供应商的数据边界基线。官方 Python SDK 可减少协议维护，但会增加依赖；首版选直接 HTTP 薄适配。直接将 Jev 概率套用现有 LLM 的 `0.6` 门槛没有校准依据，不采纳。

主要风险是把不同主体、时间或条件下的兼容事实误合并，以及新增云端数据外发。离线评测需覆盖这些反例和注入文本；旁路及接管不得以 `--dry-run` 当作零出网保证。配置回滚只能停止后续调用，不能自动撤销已经执行的治理操作。

## 未决问题

- 哪些项目及事实允许发往 TypeSafe？账号的数据保留与删除条款是否满足要求？
- 中文、英文和混合语言切片的可接受误治理上界及覆盖率是多少？
- 固定模型版本的可用期限、部署地点实测延迟和实际 token 成本如何？
- 旁路运行预算、服务故障熔断与审计保留期限如何配置？
